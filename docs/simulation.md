# Simulation: gz-sim Harmonic on ROS 2 Jazzy

The stack ran on Gazebo Classic 11 with ROS 2 Humble until October 2026. Classic
reached end of life in January 2025, so it was migrated to modern Gazebo
(gz-sim). This page records which combination was chosen and why, what was kept
equivalent, and what the migration turned up.

## Why Jazzy with Harmonic

The ROS 2 and Gazebo projects publish official pairings in REP 2000, and only
the paired combination gets binary `ros_gz` packages built against the matching
simulator.

| Pairing | Status in October 2026 | Verdict |
|---|---|---|
| Humble + Gazebo Classic 11 | Classic end of life January 2025 | the thing being replaced |
| Humble + Fortress | official pairing, but Fortress end of life September 2026 | would be migrating onto another end-of-life simulator |
| **Jazzy + Harmonic** | **official pairing; both long-term releases; Jazzy supported to May 2029, Harmonic to September 2028** | **chosen** |
| Kilted + Ionic | official pairing, short-term releases | not a base to build on |

Jazzy's `ros-jazzy-ros-gz` packages depend on the `gz_*_vendor` packages, which
carry Harmonic. Installing `ros-jazzy-ros-gz` therefore brings the matching
simulator with it and nothing has to be pinned by hand, which is the property
that made the old Humble and Classic pairing fragile. Nav2, `robot_localization`
and `cartographer_ros` are all released for Jazzy.

Versions in use (from the CI container and the image): gz-sim 8.15, Nav2 1.3.13,
`ros_gz_bridge` 1.0.24, tf2 0.36.23, Cyclone DDS.

## What was kept equivalent

The point of the migration was the same robot in the same warehouse, so the
localisation and navigation results remain comparable.

| | Gazebo Classic 11 | gz-sim 8 (Harmonic) |
|---|---|---|
| World | generated by `simulation/generate_world.py`, 30 x 12 m, 10 racking bays | same generator, same geometry; materials as colours, sun and ground plane inline instead of from the model database |
| Physics | ODE, 1 ms step | DART (gz-sim's default), 1 ms step |
| Wheels | 0.10 m radius, 50 mm tyre collision | same visual; collision a 4 mm disc in the tyre's plane (below) |
| Drive | `gazebo_ros_diff_drive`, 0.50 m track, 0.10 m wheels, 25 Nm, 10 rad/s^2 wheel acceleration | `DiffDrive` system, same track and radius, 1.0 m/s^2 linear and 4.0 rad/s^2 angular (the same limits), 25 Nm as the wheel joint effort limit |
| Wheel odometry | ENCODER source, covariance 0.001 / 0.001 / 0.01 | integrated from the wheel joints; the same covariance stamped by `odom_covariance` |
| 2D LiDAR | ray, 720 samples, 0.12-25 m, 10 Hz, 0.01 m noise | `gpu_lidar`, identical parameters |
| 3D LiDAR | ray, 1800 x 16, +-15 degrees, 0.6-40 m, 10 Hz, 0.01 m noise | `gpu_lidar`, identical parameters |
| IMU | 100 Hz, gyro 2e-4 rad/s, accelerometer 1.7e-2 m/s^2 with 0.1 m/s^2 bias | identical; the bridged covariance matches what Classic published |
| Ground truth | `gazebo_ros_p3d` on `/ground_truth/pose` | `OdometryPublisher` system on the same topic, world frame |
| Teleports for faults | `/gazebo/set_entity_state` | `/world/warehouse/set_pose` through `ros_gz_bridge` |

`ros_gz_bridge` (`src/amr_bringup/config/gz_bridge.yaml`) is now the whole
interface between simulator and stack; `tests/test_config_consistency.py`
checks every topic the stack needs is bridged and that the DiffDrive transform
is not, since the EKF owns `odom -> base_footprint`.

## Headless rendering

gz-sim has no CPU ray-cast LiDAR: `gpu_lidar` is rendered by ogre2. On a
machine without a GPU, as on a CI runner or in the container, it renders on the
CPU through Mesa's llvmpipe, and `--headless-rendering` gives it an EGL context
with no display. Nothing in the stack needs X.

## What the migration turned up

Each of these is now pinned by a test or a guard.

**The wheels turned the robot 11% too far.** DART puts a cylinder's floor
contacts at its rim edges, and with the 50 mm tyre as the wheel collision the
inner edges carried the load, so the effective track was 0.45 m against the
0.50 m DiffDrive integrates with. One commanded turn in place came out as 397
degrees by ground truth and 358 by wheel odometry, and over the full mission
the wheel-odometry heading error reached 85 degrees RMS. The wheel collision is
now a 4 mm disc in the tyre's plane (the visual is unchanged), which brings it
to 361 against 358.

**Odometry with no covariance.** `gz.msgs.Odometry` has no covariance field, so
the bridged `/odom` arrived with an all-zero matrix. `robot_localization` clamps
a zero variance to 1e-9 and would then have trusted the wheels absolutely. The
`odom_covariance` node restores the Classic values.

**A teleported static model does not move.** Classic's `set_entity_state` moved
static models; gz-sim's `set_pose` updates a static model's pose component but
neither the physics engine nor the rendering scene follows. Measured: a static
pallet moved 2.35 m ahead of the robot was reported at its new pose by
`gz model -p` while the forward LiDAR beams still read 16 m. Faults now move
`fault_pallet`, a dynamic 250 kg pallet parked outside the building.

**A Nav2 parameter that was never read.** The DWB `RotateToGoal` critic reads
`FollowPath.xy_goal_tolerance`, not `FollowPath.RotateToGoal.xy_goal_tolerance`
as every other critic parameter is named. The old setting was ignored, so the
critic ran on its 0.25 m default against a 0.20 m goal checker. With DWB's
`/evaluation` published, all 779 forward trajectories at a stall were rejected
by `RotateToGoal`, and the robot stopped 0.24 m short of every goal. Classic's
ODE base had coasted over the line; gz-sim's DiffDrive does not.

**A deadlock in tf2 0.36.22.** A minute or two into a run AMCL, the local
costmap and the global costmap would stop updating for good, while a freshly
started process saw current transforms. A `gdb` backtrace of the controller
showed the TF listener thread inside `BufferCore::testTransformableRequests`
waiting on a mutex held by the costmap's message filter thread inside
`Buffer::waitForTransform`, which was itself waiting on the first: an ABBA
deadlock, fixed upstream in tf2 0.36.23 (September 2026). The Dockerfile and CI
install tf2 explicitly so an older base image is upgraded, and both fail the
build on anything older.

**Two simulations on one host share topics.** ROS 2 discovery and gz-transport
both multicast, and containers on one Docker network hear each other: during
development another simulation on the same host exchanged `/clock`, `/tf` and
`/cmd_vel` with this one. Every compose service, the image and CI keep ROS
discovery (`ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`) and gz-transport
(`GZ_IP=127.0.0.1`) on the container's loopback. The same applies inside one
container: a gz server can outlive the launch that started it, because
`ros_gz_sim` runs it under a ruby wrapper, and a second test on the same gz
partition then shares every gz topic with it (the robot's ground truth was
seen jumping 15 m between the two worlds). Each integration test sets its own
`GZ_PARTITION`, and the test runner kills leftover servers between tests.

**Jazzy Nav2 configuration.** The built-in BT node libraries are loaded
automatically and listing them registers each twice; plugin names use `::`;
the progress checker key is plural; the behaviour server has a separate
`local_frame`; behaviour trees declare `BTCPP_format="4"`. Jazzy's controller
and planner also refuse to run on a costmap whose observation sources are late,
where Humble only warned. With the tf2 deadlock fixed the existing 0.3 s
`expected_update_rate` holds, so it was left unchanged.

## Simulation speed

On the development machine the headless simulation runs at about 0.3x to 0.8x
real time with both LiDARs, depending on what else the machine is doing. The
integration tests set the real-time factor to
0.5 (`real_time_factor` launch argument), which gives every node twice the
wall-clock time per simulated second on a loaded runner. All results are in
simulated time.
